![Same decision, any order—Strands Gemma E2B](/img/blog/decision-order.png)

“Which device directly converts chemical energy to electrical energy?”

The options were a solar-powered calculator, a wood-burning stove, a battery-powered flashlight, and a wind-powered sailboat. Presented in that order, the released checkpoint chose the battery-powered flashlight—the correct answer—with an API-returned probability of 0.5589.

Then I reversed the same four options. The question and answer choices did not change, but the checkpoint chose the solar-powered calculator at 0.5615.

| Semantic option | Original order | Reversed order |
|---|---:|---:|
| solar-powered calculator | 0.1224 | **0.5615** |
| wood-burning stove | 0.1229 | 0.0967 |
| battery-powered flashlight — correct | **0.5589** | 0.2873 |
| wind-powered sailboat | 0.1958 | 0.0545 |

Both columns are aligned to the meanings of the options, not their physical positions. This was not an index-mapping mistake. Reordering the display changed the model’s semantic answer.

That matters because this is a **decision model**: a model designed to choose among typed alternatives rather than generate an open-ended passage. Decision models can route support requests, select a policy, classify intent, assign a score, or answer yes/no questions. When list order changes their answer, presentation leaks into a decision that should depend on meaning. A harmless UI reorder can become a different routing, classification, or policy outcome.

The project asked whether this could be fixed with a **retrofit**. Here, retrofit means a narrow change around an existing released model while keeping its expensive core frozen. The goal was not to retrain Gemma from scratch. It was to change how options reach the model and how their scores are combined.

Across a controlled evaluation, reversing the complete option list changed the original model’s winning semantic answer on **851 of 3,900 questions**. The treatment, semantic alignment, task-level counts, and limitations are documented in the tagged [order-sensitivity evidence](https://github.com/manu-mishra/strands-gemma-order-stable-hybrid/blob/v0.1.0/docs/order-sensitivity-evidence.md).

## Why an ordered prompt changes the task

The original scorer placed every choice into one token sequence. Language models process sequences, so that design makes list order part of the input.

Move an option and several things change together. Its tokens occupy a different position. Its label or number changes. Different neighboring choices influence its contextual representation. The model does not see “the same answer in another display slot.” It receives a different sequence and computes different internal features.

The opening example paraphrases and reformats an ARC Easy science question from the [`allenai/ai2_arc`](https://huggingface.co/datasets/allenai/ai2_arc) dataset. The returned probabilities were rounded by the original API and renormalized by the evaluation harness, so they are useful for showing the selected answer but are not raw model scores or calibrated confidence estimates. The two orders were also separate sequential API calls. The evidence therefore supports a bounded claim: 851 observed semantic reversals for one released checkpoint, one complete-reversal treatment, and one controlled evaluation—not every possible permutation or serving environment.

Choice-order sensitivity is a broader problem. Prior work has measured [accuracy changes after reordering multiple-choice options](https://arxiv.org/abs/2308.11483), separated [position bias from option-label bias](https://arxiv.org/abs/2309.03882), and studied [order sensitivity alongside token sensitivity](https://aclanthology.org/2024.findings-acl.333/). This project focuses on a practical engineering response for one decision checkpoint.

## The constraints came first

Before designing the solution, I set four constraints.

First, the Gemma torso—the large, expensive body of the model—and the inherited Strands adapter had to remain frozen. Only small scoring components around them could be fitted. This kept the work a retrofit rather than a new foundation-model training project.

Second, the caller still had to submit one normal typed request containing all options. The runtime could create internal branches, but users should not have to make separate API calls or reconstruct answers themselves.

Third, display position could not re-enter through another door. Removing A/B/C labels would not be enough if options still began at different token positions, inherited first/last indicators, or were mapped back by row number.

Fourth, runtime behavior had to be evaluated as part of correctness. A symmetric equation on paper is not sufficient if caching, reduced precision, padding, or batching changes the model features that feed it. Any faster path had to pass numerical checks fixed before the final cases were opened.

These constraints led to two modes. `normal` judges every option independently. `compare_choices` starts from the same independent features and adds controlled comparison when the question is relational.

## How to read the architecture

The red band at the top shows the old path from left to right: one ordered prompt, one joint model run, and a winner that can move when the list is reversed. The green section below reads from top to bottom. One typed request fans out into one branch per option, and shared frozen model weights score those branches one at a time. At the bottom, the two scoring modes converge on the same semantic readback step.

From there, the paths diverge. `normal` sends the independent scores directly to the typed response reader. `compare_choices` also sends the option features through a small set-based residual—a correction layer that can compare alternatives without receiving their display positions. Both paths finally map scores back by semantic identity, so moving an option does not redefine which answer a row represents.

The diagram separates architecture from execution for a reason. The set computation is designed not to add position information, while the observed zero-flip result belongs to the complete tested runtime. The tagged [architecture and backend boundary](https://github.com/manu-mishra/strands-gemma-order-stable-hybrid/blob/v0.1.0/docs/architecture.md) records that distinction.

## `normal`: isolate first, then score

The `normal` path works step by step.

The renderer first builds the shared material: state, question, instructions, and the text that must appear before an answer. It then creates one full prompt for each semantic option. A four-choice request becomes four internal prompts, but each prompt contains exactly one choice.

Next, the renderer verifies the branch contract. Every branch must have identical bytes and tokens before its option. Every option must begin at the same logical token location. A branch must contain its complete option and no sibling option. It must not contain a generated number, letter, “first,” “last,” or any other signal derived from display order. If a long context cannot fit while preserving complete options and equal starts, strict mode raises an error instead of silently weakening the contract.

The runtime then sends each branch through the same frozen Gemma model and inherited adapter. Each branch is a complete, batch-size-one model call. It does not reuse state from another branch. From that one forward pass, the scorer extracts an answer representation and the representation at the option’s common starting point.

A small replacement scoring head applies the same learned transformation to every branch and produces one raw score, called a **logit**, for each option. A logit is simply a number used to rank alternatives before converting them into probabilities. The runtime collects those logits, applies the question type’s temperature and softmax, and constructs the expected choice, yes/no, or ordered-score response.

Finally, rows are mapped back by semantic identity rather than current position or display text. That also keeps duplicate-looking choices distinct. Exact ties use a canonical semantic rule, not “whichever row came first.”

The important property is simple: the solar calculator receives the same isolated branch whether the interface displays it first or last. Reordering the request changes branch encounter order, but not the content used to score each meaning.

Isolation is intentionally strict, and it costs more. A request with *K* options requires *K* complete model runs. That tradeoff later made prefix caching attractive.

## Isolation has a blind spot

Independent scoring works when each option can be judged against the question on its own. Intent classification, request routing, and policy matching often fit that shape.

Relational questions do not. Consider “Which plan has the second-lowest cost?”, “Which value is unique?”, or “Which provider is closest to the group average?” No isolated branch can know whether its value is second, unique, or closest because the answer depends on the other choices.

That is why the second mode exists. `compare_choices` begins with exactly the same isolated model runs, raw scores, and per-option features as `normal`. It then passes the active choices through a small **set-based** correction layer. A set-based layer treats options as a collection of items rather than as first, second, or third entries in a list.

The layer lets each option compare its content with every other active option. It also computes a shared summary of the collection and uses the same transformations for every row. It receives no slot embedding, list index, or first/last flag. The resulting correction is added to each option’s independent logit before the final probability calculation.

This design is **permutation-equivariant**. In plain language, if you shuffle the input options, the output scores shuffle in exactly the corresponding way. Put the rows back under their semantic names, and the aligned result should match within the numerical tolerance of the tested runtime. Equivariance does not mean every option gets the same score; it means an option carries its score with it when its display position changes.

The distinction between the modes is practical:

- `normal` asks, “How well does this option fit the question by itself?”
- `compare_choices` also asks, “How does this option relate to the alternatives in this request?”

The set layer is mathematically position-free given equivalent input features. That last condition matters because the frozen model and serving backend produce those features.

## Fit small components, protect the final test

Training followed the same narrow-change principle. The first stage kept the Gemma torso and inherited adapter frozen and fitted the replacement scoring head from isolated-option features. The second stage locked the complete `normal` scorer and trained only the small relational correction layer.

Architecture selection and model fitting finished before the final relational test was read. The process did not reopen that test for more tuning afterward. This firewall matters: repeatedly changing a model after seeing its final score quietly turns the final set into development data. Here, the relational comparison remained prospective—the design was fixed before its result was known.

## What the evidence says

Under the supported execution path, both `normal` and `compare_choices` produced **zero observed semantic winner changes** across the 3,900 original-versus-reversed cases. That removes the measured reversal failure without claiming universal invariance.

Broad quality stayed close to the released checkpoint. On the 3,900-question standard suite, `normal` gave up 0.51 percentage point and `compare_choices` gave up 0.54 point. On the separate typed suite, both gained 0.75 point, and on JEVBench both answered three more items correctly. The comparison mode was not a blanket upgrade: it essentially matched `normal` on these broad evaluations rather than improving them.

Its value appeared where comparison was actually required. On the locked 2,000-question relational test, `compare_choices` improved accuracy by **3.55 percentage points** over isolated `normal` scoring. A paired bootstrap—a resampling method that keeps both modes matched on the same questions—placed the 95% interval from **+2.20 to +4.90 points**. That interval describes the tested relational task families, not all decision problems.

The relational scorer also passed **100,028 mapped permutation checks** across questions with four through eight options. For four- and five-option questions, the checks covered every permutation. For six through eight options, they used deterministic balanced and cyclic permutations rather than every possible ordering. These tests measured whether scores returned to the same semantic options after remapping. They are strong conformance evidence for those inputs and that backend, not a proof across every device, precision, kernel, or serving system.

## The cache that almost won

The strict branch design repeats a long prefix—the state, question, and instructions—for every option. The obvious optimization was a **key/value prefix cache**. In a transformer, earlier tokens produce internal attention data called keys and values. A prefix cache computes that shared data once, stores it, and reuses it while processing each option suffix instead of recomputing the full prompt.

This was attractive because the residual layer was cheap; repeated Gemma encoding dominated runtime. Across the recorded cases, the cached path ranged from **0.970× to 7.102×** the performance of full recomputation. In the best cases it was more than seven times faster, although one case was slightly slower.

Speed was not the acceptance criterion by itself. Before opening the final cache cases, I fixed three required gates: aligned raw logits could differ by at most 0.03, semantic probabilities by at most 0.02, and mapped permutation error by at most `1e-6`. “Aligned” means each number was compared under the same semantic option after any reorder.

The tested cache used BF16, short for **Brain Floating Point 16**, a reduced-precision number format commonly used to make model inference faster and smaller. It failed the raw-logit gate in **8 of 14 required cases**, with a maximum difference of **0.0716** from full recomputation.

The probability and mapped-permutation gates passed, but they could not overrule the raw-logit failure. The gates protected different properties. Probabilities can compress or hide score movement, especially when softmax normalizes all choices together. A winner can also remain unchanged in one sample even when the underlying margin has shifted enough to flip a future near-tie. The prospective protocol required all three gates, so passing two was not a reason to rewrite the rule after seeing the result.

Higher-precision cache diagnostics came much closer to full recomputation, which suggests a path for future work. They did not validate the BF16 route that was tested for release. The supported runtime therefore recomputes every branch and sends no cached attention state between them.

Batching failed in a different way. A serving system often groups unrelated requests into one model call and pads shorter inputs so the batch has a common shape. Those unrelated rows are **batching companions**: they should not affect one another semantically, but they can change the numerical execution shape.

When selected requests ran alone, the tested permutations had no semantic flips. Placing those same requests in BF16 batches with unrelated padding companions caused **26 winner flips in 744 placements**. This was not prefix reuse; it was a separate cross-request batching experiment. The reference server therefore processes complete requests serially and does not dynamically batch unrelated work.

The lesson is broader than this model: **mathematical symmetry is not a serving guarantee**. A position-free scoring rule can still receive different upstream features when precision, padding, cache layout, kernels, or batch shape change. The unit that needs evidence is the architecture plus its execution route.

## Use the mode that matches the question

Use `normal` by default when each option can satisfy the question independently: classification, routing, semantic-label selection, and many policy decisions.

Use `compare_choices` when the relationship among alternatives defines the answer. Words such as *highest*, *lowest*, *second*, *closest*, *unique*, and *dominant* are useful signals that isolated scoring may be insufficient.

For both modes, the observed order-stability result belongs to a deliberately narrow contract:

- an NVIDIA L4 CUDA environment with the recorded Python, PyTorch, and Transformers versions;
- eager attention and full recomputation of every option branch;
- one branch per model call, with batch size one;
- one complete request at a time;
- semantic remapping after permutations;
- no key/value prefix cache and no batching with unrelated requests.

The loopback reference server is an evaluation and integration boundary, not hardened public infrastructure. New hardware, number formats, quantization, kernels, attention implementations, caching strategies, or batching schemes are new conformance targets and need the same kind of prospective testing.

## What this work establishes

The project began with a concrete defect: reversing the same science answers changed a battery-powered flashlight into a solar-powered calculator, and complete reversal changed 851 of 3,900 semantic winners in the controlled baseline.

The retrofit removed explicit list position from base scoring by giving each option an equal, sibling-free branch. It added a position-free comparison layer for questions that genuinely require relationships among choices. Under the supported path, both modes showed zero observed reversal differences, broad benchmark quality stayed close to the original checkpoint, and comparison improved the locked relational test by 3.55 points.

It does not establish that the model is invariant to every possible transformation. Complete reversal is not every permutation. A tested benchmark is not every domain. Temperature-one probabilities are not calibrated confidence. A set-based equation does not guarantee identical behavior under a new backend. Images remain unsupported, and the reference server is not a production security boundary.

Within those limits, the work demonstrates a practical pattern: keep the expensive model core frozen, remove display position from option encoding, add comparison only where the task needs it, and test the full serving route rather than trusting the equations alone.
